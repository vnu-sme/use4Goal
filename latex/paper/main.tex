\section{Introduction}
\label{sect:intro}
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%

%----------------------------------------------
%-------- Research context & problems ---------
%----------------------------------------------
Modern software engineering increasingly relies on models to specify a system before it is built, reducing the cost of errors discovered late in development. Within this practice, a system's requirements and its behavior are typically captured by two separate models: a process model specifies what a system does, a goal model specifies why, and combining the two has been an active research direction for over two decades~\cite{amyot2022combining}. Yet capturing both does not guarantee they agree: a process can execute exactly as specified while still failing its goal, a gap that causes rework and implementation errors in practice~\cite{alignment2019slr}.
%----------------------------------------------
%------------- State of the art ---------------
%----------------------------------------------
Several techniques relate the two directly~\cite{ghose2007validation,koliadis2006goalbpm,caballero2026alig}: an activity mapped to a goal, a workflow pattern mapped to an intentional relation, built by hand from the designer's own judgment. None revisits this correspondence automatically: if either model changes, nothing detects whether the mapping, and the consistency it was meant to guarantee, still holds.

What none provides is a shared model of system state that both could operate on directly: a process model changes that state step by step as it executes, while a goal model reads the same state to judge whether an intention is met, and only when both refer to the same state can their consistency be checked directly, instead of inferred from a hand-built mapping. Building such a state model requires, first, a vocabulary for it: neither a process model nor a goal model records the organizational facts of a system, who may hold which role, and which roles may be held together, facts a real execution still depends on.

%----------------------------------------------
%---------------- Our proposal ----------------
%----------------------------------------------
We propose ACL, an intermediate language that captures the state of the system, following the same approach Dang et al.~\cite{dang2010jucs} use to synchronize a use case model and a design model in one shared conceptual class model. BPMN~\cite{omg2013bpmn}, grounded in that same state, is the language that executes changes to it, while i*~\cite{yu1997towards}, grounded in the same state, reads it to track whether the organization's goals are met. We formalize both readings, together with ACL's own structural invariants, and give a checkpoint-trace algorithm that checks all three together at every step of one execution scenario; because ACL specifies roles explicitly, it also catches role-assignment violations as a direct consequence.

Implemented as a USE~\cite{gogolla2007use} plugin with a batch mode and a step-by-step debugger, the method is evaluated on a meeting-scheduling and an incident-response case study, confirming feasibility with and without role-compatibility constraints.

This work is guided by two research questions:
\begin{itemize}
  \item \textbf{RQ1.} How can the organizational structure of a system be formally specified during analysis, alongside its goal model and its process model?
  \item \textbf{RQ2.} How can the evolving state of a goal model and a process model be represented in a shared intermediate model, so that their consistency can be checked along one execution scenario?
\end{itemize}

This paper makes three contributions: i) a metamodel and formal state-based semantics for each of three modeling languages, ACL, an extended i*, and a simplified BPMN, grounded in one shared object system (Section~\ref{sect:overview}); ii) a checking mechanism evaluating structural, process, and goal properties together at every step of one execution, returning independent diagnostics rather than a single verdict; and iii) a USE plugin with a batch mode and a step-by-step visual debugger.

The remainder of this paper is organized as follows. Section~\ref{sect:motivation} presents the motivating example and background. Section~\ref{sect:overview} gives an overview of the approach, introducing the metamodels, their semantics, and the checking mechanism. Section~\ref{sect:toolSupport} describes tool support. Section~\ref{sect:evaluative} evaluates the approach against related techniques. Section~\ref{sect:discussion} discusses trade-offs and limitations. Section~\ref{sect:relatedWork} reviews related work. Finally, Section~\ref{sect:conclusion} concludes the paper.

\subsection{Motivating Example}
\label{subsect:umlocl}
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%

To illustrate the scope and the limits of checking a BPMN process against an i* goal model, we present \textit{MeetingScheduler}: a unit organizes a meeting among an initiator, an organizer, an optional secretary, and several participants. The i* model (Figure~\ref{fig:istar-mtg}) ties the initiator's overall goal to two conditions: the schedule is fixed, and every participant has shown up, the latter reached by collecting each participant's availability from their calendar or, failing that, a phone call from the secretary.

The BPMN model (Figure~\ref{fig:bpmn-mtg}) lays this out, one lane per role, from the initial details to the final announcement.

\begin{center}

However, checking that a process realizes its goal model is usually done through a hand-built, one-to-one correspondence between BPMN activities and i* tasks~\cite{koliadis2006goalbpm}, one that nothing keeps in sync as the process changes, so maintaining it becomes a recurring manual cost. A shared model of the two models' state transitions is a more suitable direction: Dang et al.~\cite{dang2010jucs} check i* and BPMN this way instead, tracking the correspondence as execution unfolds rather than fixing it once by hand. Applying that idea to \textit{MeetingScheduler}, however, shows the correspondence is rarely one task to one activity: reaching one task can depend on several activities, and one activity can feed several tasks.

Tracking the correspondence this way still leaves two things unconfirmed. For instance, participants here split into two groups, phoned by the secretary or checking their own calendar, so a quality like \texttt{Inclusivity} can already read as satisfied once either path fires, without confirming it held for every participant; nothing checks whether the process, once finished, has satisfied everyone rather than the goal in the abstract. Additionally, neither model can say that the same agent should not both phone participants and be counted as one of them, since none of their input languages, nor any technique surveyed in Section~\ref{sect:relatedWork}, represents organizational role. These gaps require checking i* per participant instance rather than per goal type, and a language for organizational structure alongside it, both introduced in Section~\ref{sect:overview}.

%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\subsection{Organizational Structure Modeling: MOISE}
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%

MOISE~\cite{hubner2002moise} and its extension MOISE+~\cite{hubner2007moiseplus} specify a multi-agent organization along structural, functional, and deontic dimensions. ACL (Section~\ref{sec:acl-language}) adopts only the structural one, roles, groups, and cardinality, and extends it with the entities, associations, and role-compatibility constraints that \textit{MeetingScheduler}'s second question needs and that neither MOISE nor MOISE+ provide.

\section{Overview of Our Approach}
\label{sect:overview}
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%

Figure~\ref{fig:overview} states the approach as a domain-independent methodology, applicable to any \emph{(state model, process model, goal model)} triple: a process model replays a state model into an execution path; a goal model reads that execution path into a goal path; checking the goal path yields a consistency result. This paper instantiates the triple with one concrete choice, ACL for the state model, the simplified BPMN of Part C for the process model, and the extended i* of Part B for the goal model, but nothing in Figure~\ref{fig:overview} itself is specific to that choice; a different state, process, or goal language, one with no organizational-structure notion of its own, or a stronger one than ACL, could be substituted without changing the methodology.

\begin{figure}[htbp]
\vspace{-.3em}
\begin{center}
\includegraphics[width=\columnwidth,keepaspectratio]{images/overview.png}
\vspace{-1.1em}
\begin{center}
\caption{Overview of the proposed approach.}
\label{fig:overview}
\end{center}

Formally, the execution path is a checkpoint trace $\Gamma_B = (\Sigma_0,\dots,\Sigma_n)$, a sequence of state markings, and the goal path is its counterpart on the goal side, a marking trace $M_B = (\mu_{\Sigma_0},\dots,\mu_{\Sigma_n})$, one goal marking per checkpoint. Checking compares the final marking $\mu_{\Sigma_n}$ against the root goals and an independent oracle, and reports whether the two agree; none of the three definitions above mentions ACL, i*, or BPMN by name, only a state model, a process model, and a goal model in the abstract.

%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\subsection{The ACL Language}
\label{sec:acl-language}
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%

An ACL model captures an organization's roles and groups, together with the domain entities they act on and the cardinality and compatibility constraints between them. Its core concepts, role, group, and entity, are inspired by MOISE~\cite{hubner2002moise}, and all three specialize class to inherit its properties. Two relations complete the model (Figure~\ref{fig:acl-metamodel}): ownership, always from a group to the role or child group it owns, and compatibility, between two roles. At the highest level a model is a set of groups; each group owns its child groups and roles through ownership, and two roles linked by compatibility may be held by the same agent within that group at once; any other role pair may not. ACL is designed to capture the state of a multi-agent system, spanning both its agents and the objects they act on.

\begin{figure}[htbp]
\vspace{-.3em}
\begin{center}
\includegraphics[width=\columnwidth,keepaspectratio]{images/ACLMetamodel.png}
\vspace{-1.1em}
\begin{center}
\caption{The ACL metamodel.}
\label{fig:acl-metamodel}
\end{center}
\vspace{-2.7em}
\end{center}
\end{figure}

Figure~\ref{fig:acl-mtg} illustrates ACL applied to \textit{MeetingScheduler}: a single meeting unit holds four roles, initiator, organizer, secretary, and participant, together with the properties and entity relations each carries. Two compatibilities let one agent hold two of these roles at once: the person who requests the meeting may also attend it, so initiator and participant are declared compatible, and the organizer may double as secretary to phone the participants who have no calendar, so organizer and secretary are declared compatible too. Any other pairing is left undeclared and so forbidden by default. The meeting record and the phone contacts used for those calls are domain data rather than roles, so they attach to the group as entities.

\begin{definition}[ACL model]
\label{def:acl-model}
An ACL model is a tuple
$$\mathcal{A} = (C, \mathit{Re}), \qquad C = E \uplus R \uplus G,$$
where $E$, $R$, $G$ are pairwise disjoint finite sets of entities, roles, and groups, respectively. Let $K = \{\mathsf{own}, \mathsf{cmp}, \mathsf{asc}, \mathsf{agg}, \mathsf{cps}, \mathsf{gen}\}$ be the set of relation kinds, each $k \in K$ admitting endpoint pairs $D_k$: $D_{\mathsf{own}} = G \times (G \cup R)$, $D_{\mathsf{cmp}} = R \times R$, $D_{\mathsf{asc}} = D_{\mathsf{agg}} = D_{\mathsf{cps}} = C \times E$, and $D_{\mathsf{gen}} = (E \times E) \cup (R \times R) \cup (G \times G)$. The set of relations satisfies $\mathit{Re} \subseteq \bigcup_{k \in K} (D_k \times \{k\})$.
\end{definition}

\begin{definition}[System marking]
\label{def:system-marking}
Given an ACL model $\mathcal{A}$ (Definition~\ref{def:acl-model}), a \emph{system marking} on $\mathcal{A}$ is a tuple
$$\Sigma = (\mathit{Agent}, O, \mathit{type}, \mathit{plays}, \mathit{link}),$$
where $\mathit{Agent}$ is a finite set of agents, $O$ is a finite set of role, group, and entity instances ($E$, hence $O$, already including the built-in primitive values, e.g.\ \texttt{true}, \texttt{false}), $\mathit{type} : O \to C$, $\mathit{plays} \subseteq \mathit{Agent} \times O$, and $\mathit{link} \subseteq O \times O \times K$. $\Sigma$ is \emph{valid} iff:
\begin{enumerate}[label=(\roman*)]
  \item $\forall (a,r) \in \mathit{plays}$, $\mathit{type}(r) \in R$;
  \item $\forall ((o_1,o_2),k) \in \mathit{link}$, $(\mathit{type}(o_1),\mathit{type}(o_2)) \in D_k$;
  \item $\forall o \in O$, $|\{o' \mid ((o,o'),\mathsf{own}) \in \mathit{link}\}| \le 1$;
  \item for all $a \in \mathit{Agent}$, $r_1 \neq r_2$ with $(a,r_1),(a,r_2) \in \mathit{plays}$ and a common $g$ with $((r_1,g),\mathsf{own}),((r_2,g),\mathsf{own}) \in \mathit{link}$: $(\mathit{type}(r_1),\mathit{type}(r_2)) \in D_{\mathsf{cmp}}$.
\end{enumerate}
\end{definition}

\subsection{The Extended i* Metamodel and the ISCN Oracle}
\label{sec:istar}
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%

This paper extends i*~\cite{yu1997towards} with two constructs specific enough to carry an OCL guard: quantified refinement, and an explicit condition on every goal/task. Figure~\ref{fig:istar-metamodel} gives the resulting abstract syntax: a refinement can be quantified over the instances of a role, every one of them or just one; and every goal/task carries that condition, the guard the marking semantics below evaluates.

\begin{figure}[htbp]
\vspace{-.3em}
\begin{center}
\includegraphics[width=\columnwidth,keepaspectratio]{images/IstarMetamodel.png}
\vspace{-1.1em}
\begin{center}
\caption{The extended i* metamodel.}
\label{fig:istar-metamodel}
\end{center}
\vspace{-2.7em}
\end{center}
\end{figure}

\textit{MeetingScheduler} instantiates this metamodel directly: Figure~\ref{fig:istar-mtg} is its diagrammatic concrete syntax, i* also has an equivalent textual one.

What a goal or task's status actually is at a given point in a run is not fixed by the model itself either; it takes a separate notion, a goal marking, adapted from the marking-propagation idea of Caballero-Villalobos et al.~\cite{caballero2026alig} to a boolean domain, to read that off a system marking.

\begin{definition}[Goal marking]
\label{def:goal-marking}
Given an i* model and a system marking $\Sigma$ (Definition~\ref{def:system-marking}), the \emph{goal marking} it induces is a partial function
$$\mu_\Sigma : \mathit{IntentionalElement} \times \mathit{ActorInstance} \rightharpoonup \mathbb{B}$$
defined exactly on pairs $(e,t')$ with $t' \in O_\Sigma$; for $t' \notin O_\Sigma$, $\mu_\Sigma(e,t')$ is undefined, i.e.\ $e$ does not apply to $t'$ in $\Sigma$. For $(e,t') \in \mathrm{dom}(\mu_\Sigma)$, its value is computed recursively on the structure of $e$:
$$\mu_\Sigma(e,t') = \begin{cases}
\mathit{guard}(e)(t',\Sigma) & \text{if } e \text{ is a leaf goal/task}, \\
\bigwedge_{c \in C} \mu_\Sigma(c,t') & \text{if } e \text{ is AND-refined by } C, \\
\bigvee_{c \in C} \mu_\Sigma(c,t') & \text{if } e \text{ is OR-refined by } C.
\end{cases}$$
A \texttt{make}/\texttt{help} contribution from $e$ sets its target quality's marking to $\mu_\Sigma(e,t')$, a \texttt{hurt}/\texttt{break} contribution to $\neg\mu_\Sigma(e,t')$; a \texttt{forall}-quantified refinement aggregates $\bigwedge$ over every matching $t'' \in O_\Sigma$, \texttt{pick} aggregates $\bigvee$.
\end{definition}

In \textit{MeetingScheduler}, a participant's timetable counts as collected as soon as either a phone call or a calendar check succeeds, an OR-refinement; and phoning every participant without a calendar counts as done once one secretary succeeds, not every one, a \texttt{pick}.

The word \texttt{Pending} is a display label for $\mu_\Sigma(e,t') = \mathit{false}$ with $t' \in O_\Sigma$, not a third semantic value; $t' \notin O_\Sigma$ (undefined) is what an earlier, three-valued formulation called \texttt{UNKNOWN}. Because Part D's failure lists range only over $\mathrm{dom}(\mu_{\Sigma_n})$, an actor instance absent from the trace is skipped automatically, never counted as a failure.

An \texttt{.iscn} file is the instance-level companion to \texttt{.istar}: it assigns the expected final marking for chosen actor instances, compared by Part D against the actual $\mu_{\Sigma_n}$ (Definition~\ref{def:goal-marking}).

\subsection{The Simplified BPMN Metamodel and State-Transition Semantics}
\label{sec:bpmn}
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%

A \texttt{.bpmn2} specification fixes a process as activities, gateways, and events linked by sequence flow; it inherits BPMN's~\cite{omg2013bpmn} pool/lane/activity/event/gateway vocabulary and adds an optional OCL \texttt{pre}/\texttt{post}/\texttt{effect} on each activity and an OCL \texttt{guard} on each gateway flow, so that every state change is a single \texttt{effect} SOIL statement, with no other domain mutation.

A process model needs to say more than which activities happen in which order: each activity's effect on the state that ACL and i* both read must be pinned down too, and a gateway's branch condition must be evaluable against that same state. Figure~\ref{fig:bpmn-metamodel} gives BPMN's abstract syntax for exactly this: a model groups one or more processes, each partitioned into lanes of flow elements, activities, tasks, sub-processes, or call activities, and events, start, end, or intermediate, linked by sequence flow within a process and message flow across processes; gateways sit among the flow elements too, each carrying a kind, exclusive, parallel, inclusive, or event-based. \texttt{pre}, \texttt{post}, \texttt{effect}, and \texttt{guard} attach directly to this metamodel rather than to a separate annotation layer, each written over the same class model as ACL (Section~\ref{sec:acl-language}) and i* (Section~\ref{sec:istar}).

\begin{figure}[htbp]
\vspace{-.3em}
\begin{center}
\includegraphics[width=\columnwidth,keepaspectratio]{images/BPMNMetamodel.png}
\vspace{-1.1em}
\begin{center}
\caption{The simplified BPMN metamodel.}
\label{fig:bpmn-metamodel}
\end{center}
\vspace{-2.7em}
\end{center}
\end{figure}

\textit{MeetingScheduler} instantiates this metamodel too, and only a subset of it: Figure~\ref{fig:bpmn-mtg} (Section~\ref{subsect:umlocl}) already gave its concrete syntax, annotated activities and exclusive-gateway-guarded flows, one lane per role, from the initial-details activity to the final announcement, with the gateway guarding the phone-versus-calendar branch for collecting a participant's availability.

\label{sec:bpmn-semantics}
What such a schema actually does at runtime, in what order its activities run and what each run changes in the state that ACL and i* both read, is not fixed by the schema itself; it takes a separate notion, a checkpoint transition system, to pin that down.

\begin{definition}[BPMN model]
\label{def:bpmn-model}
A BPMN model over an ACL model $\mathcal{A}$ (Definition~\ref{def:acl-model}) is a tuple $B = (Act, Gw, Ev, \mathit{Flow}, \mathit{lane}, \mathit{pre}, \mathit{post}, \mathit{effect}, \mathit{guard})$, instantiating Figure~\ref{fig:bpmn-metamodel}:
\begin{itemize}
  \item $Act$, $Gw$, $Ev$ are pairwise disjoint finite sets of activities, gateways, and events;
  \item $\mathit{Flow} \subseteq N \times N$, for $N = Act \cup Gw \cup Ev$, is the sequence-flow graph, with a unique start event $s \in Ev$ having no incoming edge;
  \item $\mathit{lane} : Act \to R$ assigns each activity the ACL role responsible for it;
  \item $\mathit{pre}, \mathit{post}, \mathit{effect} : Act \rightharpoonup \mathit{OCL}(\mathcal{A})$ are partial functions giving each activity an optional precondition, postcondition, and effect;
  \item $\mathit{guard} : \mathit{Flow} \rightharpoonup \mathit{OCL}(\mathcal{A})$ optionally guards a flow leaving a gateway in $Gw$.
\end{itemize}
\end{definition}

Fixing $B$ over the same $\mathcal{A}$ that every system marking (Definition~\ref{def:system-marking}) is an instance of is what lets $\mathit{pre}$, $\mathit{post}$, $\mathit{effect}$, and $\mathit{guard}$ be evaluated directly on any $\Sigma$, with no separate translation step, the trade-off motivating the simplified dialect above.

Two things this schema still leaves open: the order in which $Act$ actually runs, and what running it produces as a trace of system markings.

\begin{definition}[Execution order]
\label{def:execution-order}
Given a BPMN model $B$ (Definition~\ref{def:bpmn-model}), its activities $A = \{a_1,\dots,a_n\} = Act$ are ordered by a topological sort (Kahn's algorithm) of $(N, \mathit{Flow})$ starting from $s$. $B$ executes along this single, fixed sequence, without evaluating $\mathit{guard}$ to choose among competing successors, a simplification discussed in Section~\ref{sect:discussion}.
\end{definition}

A translator compiles the \texttt{.aol} snapshot into an initial SOIL script; executing it, not any hand-written SOIL, is how the system marking $\Sigma_0$ below is obtained.

\begin{definition}[Checkpoint transition system]
\label{def:checkpoint-trace}
Let $B$ be a BPMN model over $\mathcal{A}$ (Definition~\ref{def:bpmn-model}) and $\Sigma_0$ a system marking on the \emph{same} $\mathcal{A}$ (Definition~\ref{def:system-marking}) — here, the one \texttt{mtg\_initial.aol} compiles to. The \emph{checkpoint transition system} induced by $B$ and $\Sigma_0$ is
$$\Gamma_B = \langle \Sigma, A, \Sigma_0, \rightarrow \rangle, \quad \Sigma=\{\Sigma_0,\dots,\Sigma_n\},$$
where $(\Sigma_{i-1}, a_i, \Sigma_i) \in\, \rightarrow$ iff $\Sigma_i = \mathit{effect}(a_i)(\Sigma_{i-1})$ ($\Sigma_i = \Sigma_{i-1}$ if $\mathit{effect}(a_i)$ is undefined), for $1 \le i \le n$. Every $\Sigma_i$ is itself a system marking on $\mathcal{A}$ — this is the whole answer to ``how do $B$ and $\mathcal{A}$ together generate an execution trace'': $\mathcal{A}$ fixes the space of valid $\Sigma_i$, $\Sigma_0$ anchors the trace in it, and $B$'s $\mathit{effect}$, taken in the order of Definition~\ref{def:execution-order}, walks it forward one checkpoint at a time.
\end{definition}

By Definition~\ref{def:execution-order}, $\Gamma_B$ has one outgoing transition per state: a single \emph{run} $\Sigma_0 \xrightarrow{a_1} \Sigma_1 \xrightarrow{a_2} \cdots \xrightarrow{a_n} \Sigma_n$, a checkpoint trace rather than a branching system, deliberately checking one concrete execution rather than the full reachable state space (Section~\ref{sect:discussion}).

\begin{definition}[Guarded properties]
\label{def:guarded-properties}
Every $a_i$ may carry OCL booleans $\mathit{pre}(a_i)$, $\mathit{post}(a_i)$; unlike $\mathit{effect}$, these do not alter $\rightarrow$, but are evaluated by Part D's mechanism, $\mathit{pre}(a_i)$ at $\Sigma_{i-1}$ and $\mathit{post}(a_i)$ at $\Sigma_i$.
\end{definition}

%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\subsection{Checking i* and BPMN over State Transitions}
\label{sec:checking}
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%

As in Definition~\ref{def:guarded-properties}, every i* intentional element carries an OCL guard, evaluated over $\Gamma_B$ via the goal marking $\mu_{\Sigma_i}$ of Definition~\ref{def:goal-marking}, one $\mu_{\Sigma_i}$ per checkpoint.

Formally, the \texttt{.iscn} oracle (Section~\ref{sec:istar}) is a partial function of the same type as a goal marking, $\mathit{oracle} : \mathit{IntentionalElement} \times \mathit{ActorInstance} \rightharpoonup \mathbb{B}$, defined only on the elements/instances it observes; an instance resolves first by exact \texttt{.aol} role-instance identity, else by an \texttt{.aol} agent identity resolving to exactly one role instance, rejecting ambiguous agents.

With $\Gamma_B$, $\mathit{pre}/\mathit{post}$, $\mu_\Sigma$, and $\mathit{oracle}$ all defined, the four failure lists are:
\begin{align*}
\mathit{aclFailures} &= \{\, i : \Sigma_i \not\models \mathit{Inv},\ \text{some invariant } \mathit{Inv},\ i \text{ minimal} \,\}, \\
\mathit{bpmnFailures} &= \{\, a_i : \mathit{pre}(a_i)(\Sigma_{i-1}) = \mathit{false} \,\} \cup \{\, a_i : \mathit{post}(a_i)(\Sigma_i) = \mathit{false} \,\}, \\
\mathit{goalFailures} &= \{\, (g,t') \in \mathrm{dom}(\mu_{\Sigma_n}) : g \text{ a root goal}, \mu_{\Sigma_n}(g,t') = \mathit{false} \,\}, \\
\mathit{oracleFailures} &= \{\, (e,t') \in \mathrm{dom}(\mathit{oracle}) \cap \mathrm{dom}(\mu_{\Sigma_n}) : \mu_{\Sigma_n}(e,t') \ne \mathit{oracle}(e,t') \,\}.
\end{align*}
$\mathit{aclFailures}$ is \emph{fail-fast}, reporting only the minimal violating $i$, since later $\Sigma_j$ may already be invalid; a non-empty result already makes the trace non-conformant before $\mathit{goalFailures}$/$\mathit{oracleFailures}$ are computed. $\mathit{bpmnFailures}$ collects every independent violation, likewise non-conformant on its own. $\mathit{goalFailures}$ and $\mathit{oracleFailures}$ are evaluated once, at $\Sigma_n$, only after a clean replay; restricting both to $\mathrm{dom}(\mu_{\Sigma_n})$ (Definition~\ref{def:goal-marking}) skips any actor instance absent from the trace automatically, rather than counting it as a failure.

Three situations from Section~\ref{subsect:umlocl} show why four separate lists matter. \emph{ACL}: if one agent holds both \texttt{Secretary} and \texttt{Participant} in the same \texttt{MeetingUnit}, neither BPMN nor i* notices, since each checks its own actor type independently, but $\mathit{aclFailures}$ flags it immediately, since \texttt{Secretary~<->~Participant} is never declared compatible. \emph{Goal}: if the trace stops right after \texttt{announceMeeting}, before some \texttt{Participant} executes \texttt{participate}, $\mathit{bpmnFailures} = \emptyset$, yet $\mu_{\Sigma_n}(\texttt{HaveMeetingOrganized}, \cdot) = \mathit{false}$ since the root goal also needs \texttt{MeetingAttendedByParticipant}, so $\mathit{goalFailures} \ne \emptyset$. \emph{Oracle}: if a \texttt{Participant} with no calendar is wrongly marked Fulfilled on \texttt{CollectFromCalendar} instead of the oracle's Pending, an authoring slip that still lets every root goal reach \texttt{true} through the phone path, $\mathit{goalFailures} = \emptyset$ but $\mathit{oracleFailures} \ne \emptyset$. $\mathit{bpmnFailures}$ alone would have passed the second case, and $\mathit{goalFailures}$ alone the third.

%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\section{Tool Support}
\label{sect:toolSupport}
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%

The method is implemented as a USE plugin, adding i*, BPMN, and ACL each as a compiler/metamodel/view triple following USE's own convention for a new modeling language, with OCL embedded directly in i*.

Two checking modes are exposed. The \emph{batch mode} runs the pipeline of Section~\ref{sect:overview} once over the five inputs of Figure~\ref{fig:overview} and reports the four failure lists, suited to answering ``is the system conformant, and where is the first problem''. The \emph{step-by-step debugger} instead replays the checkpoint trace one activity at a time, coloring the i* diagram by goal/task status (\texttt{FULFILLED}/\texttt{PENDING}/violated/\texttt{UNKNOWN}) in sync with the BPMN diagram, so a user sees the exact point and diagram where the state diverges from expectation, rather than a text log of failures.

The tool has been applied to \textit{MeetingScheduler}, which exercises the ACL role-compatibility check, and to an \textit{Incident Response} process with no role-compatibility constraints; both run through the same pipeline unchanged, confirming feasibility with and without organizational-structure constraints.

%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\section{Evaluation}
\label{sect:evaluative}
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%

RQ1 is answered by the ACL, extended i*, and simplified BPMN metamodels (Sections~\ref{sec:acl-language}--\ref{sec:bpmn}); RQ2 by the state-transition semantics and checking algorithm (Sections~\ref{sec:bpmn-semantics}--\ref{sec:checking}) and the tool of Section~\ref{sect:toolSupport}. The rest of this section positions these answers against the three representative techniques of Section~\ref{sect:intro}.

Ghose and Koliadis's~\cite{ghose2007validation} Description-Logics classification is fully automated and decidable, but reasons at a single point in time and cannot represent execution order (Section~\ref{sect:relatedWork}). GoalBPM~\cite{koliadis2006goalbpm} tracks effects along an execution trajectory, closer in spirit to the checkpoint trace here, but the whole pipeline is manual, whereas this method infers checkpoints and snapshots automatically from OCL already in the models. Caballero-Villalobos et al.~\cite{caballero2026alig} offer the strongest guarantee, a verdict holding for every reachable execution rather than one trace; this method trades that guarantee for running directly on existing USE/SOIL infrastructure, and, unlike all three, adds organizational-role constraints none of them can express.

None of the three would catch the \texttt{Secretary}/\texttt{Participant} conflict of Section~\ref{sec:acl-language} on \textit{MeetingScheduler}, not from individual weakness but because their input languages have no concept for a role-compatibility constraint. The proposed method does not supersede them on the goal--process dimension; it adds an orthogonal organizational dimension, at the cost of checking one concrete trace instead of every reachable one (Section~\ref{sect:discussion}).

%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\section{Discussion}
\label{sect:discussion}
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%

\subsection{Separating four kinds of failure}
Splitting the result into \texttt{aclFailures}, \texttt{bpmnFailures}, \texttt{goalFailures}, and \texttt{oracleFailures}, rather than one verdict, mirrors who actually fixes each: an organization's role-compatibility policy, a BPMN redesign, and a business goal change are usually made by different people at different times, so routing failures by kind is faster than one combined verdict. When a single checkpoint violates two lists at once, for example an agent holding an incompatible role that also breaks an activity precondition, which is reported first is currently just an implementation order, ACL invariants fail-fast before BPMN pre/postconditions, not necessarily the right business priority.

\subsection{One trace, not every trace}
Checking one concrete SOIL scenario answers whether that scenario is consistent, not whether every scenario is, the stronger guarantee that weak/strong compliance in Caballero-Villalobos et al.~\cite{caballero2026alig} gives for the goal--process pair alone. This is deliberate: it trades that generality for running immediately on the existing USE/SOIL engine, instead of building and independently verifying a new marking-propagation semantics from scratch. Because the checkpoint compiler takes the scenario as an ordinary parameter, the pipeline could be re-run over several scenarios to raise coverage, though without the same formal guarantee as full state-space exploration.

\subsection{Limitations}
\emph{Coverage.} A single topological sort, not gateway semantics, fixes activity order, so a branch off that order is simply not exercised; a \texttt{PASS} is a statement about the trace checked, not every trace. \emph{Scenario quality.} An under-populated SOIL scenario can let the root-goal check silently skip actors absent from the trace. \emph{Fail-fast masking.} A second ACL violation occurring after the first may only surface on a subsequent run. \emph{Pairwise compatibility only.} The compatibility rule handles role pairs, not higher-arity constraints such as ``at most two of three roles at once''. \emph{Evaluation scope.} The evidence rests on two case studies; broader validation and a running-time measurement are left for future work.

%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\section{Related work}
\label{sect:relatedWork}
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%

A first line of work establishes a \emph{structural} correspondence, deciding once, over the models as written, whether a goal model's decomposition matches a control-flow pattern of the process. Ghose and Koliadis~\cite{ghose2007validation} translate a GRL goal model and a BPMN process into Description Logics and classify each workflow-pattern/intentional-relation pair with a Pellet reasoner, later extended to choreographies~\cite{groner2014vadl}; Guizzardi et al.~\cite{guizzardi2014vemi} assert the same correspondence between an i* metamodel and a model-driven-development metamodel, flagging unmappable elements before a transformation runs; Eshuis and Ghose~\cite{eshuis2021consistency} assert it between a goal model and a declarative case-management schema.
%Roelens et al.~\cite{roelens2019pga} assert the same correspondence but report it as a continuous score rather than a pass/fail verdict, heat-mapping a strategy-to-process value hierarchy.
The limitation is structural, not behavioral: a process can satisfy every correspondence rule and still, once executed, never reach the root goal, a failure none of these techniques is positioned to observe.

A second line of work asserts a \emph{behavioral} claim instead, giving the process an execution semantics and checking whether goal satisfaction holds along what it actually does. GoalBPM~\cite{koliadis2006goalbpm} checks one hand-extracted trajectory against KAOS temporal patterns; Dang et al.~\cite{dang2010jucs} derive the same single-trace claim automatically, synchronizing two scenarios via a triple graph grammar and OCL, the framework this paper builds on; Caballero-Villalobos et al.~\cite{caballero2026alig} check every reachable execution instead, translating both models into a shared transition system and deciding weak or strong compliance by two-way graph traversal, with proofs of correctness and completeness.
%Guizzardi and Reis~\cite{guizzardi2012align} check one trajectory with a continuous verdict instead, propagating a satisfaction score along classified execution paths.
%A separate cluster keeps this same behavioral machinery but drops the structured goal model entirely, checking a process against a contract~\cite{governatori2006compliance}, a regulation~\cite{ghose2007auditing}, an LTL pattern~\cite{awad2009visualization}, or a real log~\cite{aalst2005conformance} instead.
The limitation scales with the claim: a single trace says nothing about the branches never taken, and the exhaustive claim forces even a branch never meant to reach the goal, such as a rejected request, to still count as compliant, which the authors themselves call business-irrational.

Neither line's input language models organizational role, so a process can pass every structural or behavioral check above and still let one agent occupy two roles that were never meant to coexist. Section~\ref{sect:overview} closes this gap: it composes role-compatibility invariants, specified in ACL and grounded in MOISE~\cite{hubner2002moise} (Section~\ref{sec:acl-language}), into the same checkpoint trace that already carries the automatic single-trace claim of Dang et al.~\cite{dang2010jucs} and the structural-correspondence claim of Guizzardi et al.~\cite{guizzardi2014vemi}.

%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
\section{Conclusion}
\label{sect:conclusion}
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%

This paper has presented ACL, an organizational structure language, together with formal state-based semantics for ACL, an extended i*, and a simplified BPMN that let all three be checked together over a single checkpoint trace on one USE/OCL object system. This work makes three contributions. First, each of the three languages is given a metamodel, a concrete instance-level companion, and formal semantics, system-marking validity for ACL, goal marking for i*, checkpoint-trace execution for BPMN, all sharing one object system. Second, a checking mechanism evaluates ACL invariants, BPMN pre/postconditions, and i* goal satisfaction over one checkpoint trace derived from a concrete execution scenario, returning four independently owned diagnostics rather than a single verdict. Third, a plugin integrated into the USE environment supports both a batch checking mode and a step-by-step visual debugger.

Through the \textit{MeetingScheduler} case study, the method has been shown to detect a role-compatibility violation that neither an i*-only nor a BPMN-only check can see, while an incident-response case study confirms the pipeline is equally applicable to models without organizational-structure constraints. As discussed in Section~\ref{sect:discussion}, the method checks a single concrete execution trace rather than every reachable one, and its compatibility rule currently handles role pairs rather than higher-arity constraints. Future work includes re-running the pipeline over multiple scenarios to increase coverage, extending compatibility constraints beyond pairs of roles, and a broader empirical evaluation across the additional case studies already available in the project, together with a measurement of running time as a function of scenario size.
